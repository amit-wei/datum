## 1. Quality reference for writing functions

1. **A function is something the block does, named verb + object, not a thing or a state.** Right: "Record a payment"; wrong: "Payment database", "Authenticated". Sources: NASA defines functional analysis as "identifying, describing, and relating the functions a system should perform" (SEH 4.3.1.2.2, VERIFIED). Verb-noun form and the pitfalls "state names", "starting with a noun", "vague names" come from INCOSE-derived material: PPI https://ppi-int.com/?p=7156 and Haskins/INCOSE paper (VERIFIED-secondary). The function name is not the function: the written description carries the meaning (PPI, VERIFIED-secondary).
2. **Avoid empty verbs (provide, support, allow, handle, facilitate).** Right: "Convert a bill to a summed total"; wrong: "Provide billing support". FMEA training deck via search summary (VERIFIED-secondary); INFERRED that an empty verb hides an unwritten function.
3. **State what, not how.** Right: "Keep the notes the user wrote"; wrong: "Store notes in SQLite". NASA Appendix C: "Requirements should state WHAT is needed, NOT HOW" (VERIFIED). Jackson separates the problem domain from the machine (VERIFIED-secondary, https://en.wikipedia.org/wiki/Problem_frames_approach).
4. **Describe each function by inputs, outputs, failure modes, consequence of failure.** Right: "Import a file: in = path, out = parsed records, fails on unreadable file -> user told which file". NASA SEH 4.3.1.2.2 (VERIFIED). Note this makes failure a property of the function, not a separate function.
5. **A function is not a performance, constraint or quality.** "Respond within 200 ms", "Run offline", "Be secure" are requirements on a function (NASA splits functional, performance, interface requirements, SEH 4.2.1.2.2, VERIFIED; the example turns "TVC shall provide vehicle control" into measured sub-requirements). Right: function "Search notes"; requirement "returns in 200 ms". INFERRED for the exact datum rule: if the sentence has no verb a user or neighbour block could observe being done, it is a requirement.
6. **A function is not an interface.** "Give/receive X" between blocks is a flow, not a function. Right: flow "query text" from user to Search notes; wrong: function "Receive query". NASA lists interfaces as a separate third step of functional analysis (SEH 4.3.1.2.2, VERIFIED). Pitfall list: muddling control flow with item flow; "omitting item flows to out-of-boundary functions" (PPI, VERIFIED-secondary). INFERRED: for software, a function whose only content is "accept input" or "return output" is a flow.
7. **A function is not a mechanism or component.** Right: "Keep a history of edits"; wrong: "Event bus". Armstrong (INCOSE 2013 talk) flags blocks with "No Verb!" mixing components with functions (VERIFIED-secondary, search summary, the PDF returned 403). Pendentive L3: product functions that were infrastructure capabilities (VERIFIED, repo research).
8. **A guard or mitigation is not a function on its own.** Right: function "Delete a note" with a requirement "asks for confirmation" and a hazard recorded; wrong: function "Prevent accidental deletion". NASA puts failure modes and consequence on the function (item 4, VERIFIED). INFERRED: in datum, hazards belong in `losses-and-hazards` and requirements answer them; a function exists only if someone wants the thing done. Exception: a mitigation that adds user-visible behaviour (a recovery path) is a function that serves a failure scenario.
9. **At product level every function serves a scenario; below, it decomposes a parent function.** Right: "Find a note I wrote last week" serves scenario "return to old work"; wrong: "Index text" at product level (belongs below, under Search). NASA: functional analysis is "usually based on the ConOps" and "any specified operational usage of the system can be traced in an end-to-end path" (SEH 4.3.1.2.2, VERIFIED). Cockburn: use cases are goals of actors (VERIFIED-secondary). Pendentive L3 (VERIFIED repo).
10. **Choose the level: the function should be a goal one actor finishes in one sitting ("sea level") at product level.** Right: "Place an order"; too high: "Run the shop"; too low: "Validate postcode". Cockburn goal levels summary / user-goal / subfunction, naming "verb + goal", test by asking "why?" upward and "how?" downward (draft extract VERIFIED; the sea-level rule and "too low" examples VERIFIED-secondary). Below product level, use the level rule of datum (design-notes) instead; Cockburn levels do not apply to internal blocks (INFERRED).
11. **Decompose by asking what the parent function needs in order to be done, and write the result under the parent.** Right: Search notes -> Match query to notes; Rank matches; Show matches. NASA: "sub-functions are recognized as part of larger functional areas"; "there will almost certainly be alternative ways to decompose functions... the outcome is highly dependent on the creativity, skills and experience" (SEH 4.3.1.2.2, VERIFIED). Consequence: there is no unique right tree; check by coverage and traceability, not by matching an answer key (INFERRED).
12. **Do not decompose by mechanism or component.** Right: children are things done in order; wrong: children are "UI layer", "storage layer". INFERRED from NASA allocation as a separate step (allocate to elements after the functions exist, SEH 4.3.1.2.2 step 2, VERIFIED) and datum's own split between decomposition (`parent`) and allocation (`contributes_to`).
13. **Include the non-happy functions the system must do.** Right: "Recover the last session after a crash", "Start up with no data", "Export all data for backup". Wrong: a list with only the features users asked for. Cockburn: every deviation and error handled in extensions, and every stakeholder's interest satisfied (VERIFIED-secondary guide). NASA: each function has failure modes and consequences (VERIFIED). Startup, shutdown, maintenance, internal state change as functions: INFERRED (classic SE lifecycle modes; the sources read do not list them for software).
14. **Include functions for every stakeholder, not only the primary user.** Right: "Let the maintainer see which version is installed". Cockburn stakeholder-interest rule (VERIFIED-secondary guide). The actors outside the block are the `external` type in datum (INFERRED).
15. **Separate create/read/update/delete lists from goals.** Wrong: five functions "Create/Read/Update/Delete/List note". Right: the goals behind them ("Capture a thought", "Correct a note"). "CRUD mania" listed as a use-case error (VERIFIED-secondary guide). Hardware parallel: none.
16. **Do not put a function in because it is easy to build or "nice to have" (dashboards, metrics, admin screens).** Right: every function cites a scenario or parent; wrong: "Show usage statistics" with no one asking. NASA checklist: "Are all described functions necessary and together sufficient" (Appendix C, VERIFIED). Parnas: users "tend to overstate their requirements" (VERIFIED). Pendentive L3 and L4 (VERIFIED repo).
17. **Functions are independent of how many times, who, or when unless the flow says so.** Order is recorded in the flow (functional flow / sequence), not in the name. Right: "Authorise payment" then "Record payment" as a flow; wrong: "Authorise payment then record it". FFBD: "time sequence of functional events" (NASA glossary, VERIFIED). Appendix F method not read.
18. **A function name should not be the start or end of another function, nor a negative.** Wrong: "Start search", "Never lose data". PPI pitfall list (VERIFIED-secondary). The negative becomes a requirement or hazard answer (INFERRED).
19. **One function, one reason to exist; split a function that does two things.** Right: "Save a note" and "Sync notes to another device". Parnas: "avoid components that perform more than one function" and finds the smallest possible increments in capability (VERIFIED). Datum's stopping rule matches (design-notes).
20. **Record why the function exists as a link, once.** Right: `serves: [SCN-..]` or `parent: FUN-..`. NASA: functional analysis "identifies and links system functions, trade studies, interface characteristics, and rationales to requirements" (VERIFIED). ECSS function tree is "the starting point for the Product Tree and a basic structure for preliminary technical requirements" and should give "the complete list of functions" (ECSS-E-ST-10C Annex H DRD, VERIFIED-secondary via search result https://ecss.nl/wp-content/uploads/2021/08/ECSS-E-ST-10C-Rev1(15February2017)AnnexH_Function-tree.docx; not opened).

## 2. Checks a reviewer or script can run

Script-checkable (structure):
- C1. Every function at product level has `serves` with at least one scenario that resolves. Every non-product function has `parent` that resolves. (NASA traceability, SEH 4.3.1.2.2, VERIFIED; datum design-notes.)
- C2. Every scenario step is covered by at least one function (a function-to-step mapping, either side stored once). INFERRED from "any specified operational usage can be traced in an end-to-end path" (SEH, VERIFIED) and the existing end condition in the notes.
- C3. Every function has at least one requirement `of: FUN` (datum's requirements end condition; NASA Appendix C "functions necessary and together sufficient", VERIFIED, wording only).
- C4. Name check: begins with a verb from a word list; not in a banned list (provide, support, handle, allow, facilitate, manage, process, ensure). Too long (more than ~10 words) suggests two functions. PPI, FMEA deck (VERIFIED-secondary), threshold INFERRED. Warning only, not an error.
- C5. Mechanism words in the name or statement (database, API, queue, cache, class, microservice, table, endpoint, library names): flag. INFERRED, supported by "WHAT not HOW" (VERIFIED).
- C6. Modal check: a function statement must not contain "shall", a number plus a unit, "within", "at least": those belong to requirements. INFERRED.
- C7. Fan-out: a parent with exactly one child is suspect (the child restates the parent), and a parent with more than about 7 children is suspect (missing level). INFERRED; no source gives the number.
- C8. Duplicate check: two functions with the same verb and object in the same block. INFERRED.
- C9. Orphan check: functions no part `contributes_to` (allocation), at synthesis. NASA step 2, datum notes.
- C10. Flows: every flow names a source and sink among the block's functions or externals, and every function has at least one in and one out unless it is a pure source or sink of an external. NASA "inputs, outputs" (VERIFIED); N2 diagram diagonal-and-off-diagonal idea (https://en.wikipedia.org/wiki/N2_chart, VERIFIED-secondary).

Reviewer-judged (needs reading):
- R1. Level test: ask "why is this done?" and "how?" and check the parent and children appear in the model (Cockburn, VERIFIED-secondary).
- R2. Needs test: delete the function; does a scenario step lose its doer? If not, it is not needed (INFERRED).
- R3. Substitution test: if the stated technology changed, would the function still read true? If not, it is a mechanism (INFERRED from WHAT/HOW).
- R4. Observability test: could a person watching the block from outside see it being done? If not, it is a property or an internal part (INFERRED; Jackson's problem domain, VERIFIED-secondary).
- R5. Negative-space prompts, one per category: startup, shutdown, first use with empty state, upgrade, backup and restore, failure of each external, bad input, help or diagnosis for the maintainer. Each yields a function, a requirement on an existing function, or a recorded "out of scope". (Cockburn extension walk, VERIFIED-secondary; list INFERRED.)
- R6. Stakeholder pass: for each external and each stakeholder in the elicitation record, name the function that serves their interest, or mark it out of scope. (Cockburn, VERIFIED-secondary.)
- R7. Alternatives pass: ask for one other way to decompose; if two exist and give different parts, record it as a decision, not a function (NASA "alternative ways to decompose", VERIFIED).
- R8. Hazard pass: for each function, what loss can it cause? (NASA "failure modes, consequence of failure", VERIFIED; datum's losses-and-hazards technique.)
- R9. Overbuilt pass: any function whose scenario is "someone might want it" gets removed or deferred (Parnas minimal subset, VERIFIED; Pendentive audit).

## 3. How scenarios and functions relate

- **Scenario first, at product level.** NASA: functional analysis is "usually based on the ConOps" (SEH 4.3.1.2.2, VERIFIED). Cockburn: goal and main success scenario at precision levels 1 and 2 before detail (draft extract, VERIFIED). Patton's story map: users' activities and steps along the backbone, features beneath (VERIFIED-secondary from https://www.barkingiguana.com/writing/user-story-mapping-seeing-the-whole). Jackson: requirements are in domain terms; the machine is specified from them (VERIFIED-secondary). All agree the order is need, then scenario, then function (INFERRED synthesis).
- **Coverage, both directions** (INFERRED, consistent with the sources above):
  1. Every scenario step has a function that does it (or an external does it, stated).
  2. Every product function serves at least one scenario.
  3. A function serving many scenarios is normal (a reuse sign); a scenario with a step shared by none is not an error.
  4. Below product level the scenarios are the parent's: a child function must trace to a parent function, and the parent's scenarios that touch the block are walked in design evaluation.
- **Granularity.** One scenario step is often one function but may be several sub-functions, or a step may be done by an external. Cockburn: the use case's steps are goals of the actor or system at one level lower (VERIFIED-secondary), so the function of a step is below sea level and the sea-level goal is the scenario. INFERRED consequence for datum: if scenarios are sea-level goals, the top-level product functions are the system's steps in those scenarios, not the goals themselves. Decide this explicitly in the writing-functions skill.
- **Failure scenarios.** Cockburn's extensions (error branches) are where error-handling functions come from (VERIFIED-secondary). So scenarios must include the main path and the notable failure paths, or error functions go missing.
- **Event storming** (VERIFIED-secondary, search summary only): events and commands give another source of functions and of internal state changes that user scenarios miss. INFERRED use: a cross-check, not a replacement.
- **Jobs to be done** (not read, INFERRED): a job statement is a need in the elicitation record, upstream of scenarios; it is not a function (it names a motive, not something the product does).

## 4. Disagreements and what does not carry over

Disagreements:
- **Function vs requirement.** NASA treats "functional requirement" as a requirement stating a function (SEH 4.2.1.2.2, VERIFIED); MIL-STD/IEEE-style functional analysis treats functions as separate objects that requirements then attach to (datum's position, consistent with IEEE 1220 order as quoted in design-notes; the standard itself not read). ECSS keeps a function tree as its own deliverable (VERIFIED-secondary). Pick: separate objects (already decided).
- **Verb-noun vs free text.** INCOSE-derived guidance wants verb-noun; NASA Rev2 does not state a form (VERIFIED, searched; nothing found). The ESA OSMoSE note says each contractor reads "function tree" differently (VERIFIED-secondary). So conventions are local; datum must define its own.
- **One tree or many.** NASA says alternative decompositions exist and the result depends on the engineer (VERIFIED). Cockburn and Patton give a stable level (sea level, backbone) (VERIFIED-secondary). Hardware wants a hierarchy; story maps want a flat-then-layered map.
- **Minimal vs complete.** Parnas wants the smallest useful subset plus small increments (VERIFIED); NASA wants a complete set before baseline (VERIFIED). Reconcile (INFERRED): complete within the increment, minimal across it.
- **Users' words.** Parnas: asking users what they can do without gives overstated needs and misses future subsets (VERIFIED); Cockburn and Patton start from asking users (VERIFIED-secondary).

Does not carry over from hardware to software (all INFERRED unless noted):
- Functions allocated one-to-one to physical components; in software a function is split across modules freely and cost of copying is near zero. Datum's "one function, one component" stopping rule is a hardware heuristic (design-notes labels it so).
- FFBD time sequences assume a single thread through a mission; software has concurrency, events and idle states, so flows are better as scenarios plus state machines (NASA also keeps state analysis separate, Appendix F title, VERIFIED).
- Hardware functions have energy, mass and signal flows; software flows are data and control. Muddling control flow and item flow is a named error (PPI, VERIFIED-secondary), but item flow is cheap in software, so the risk is under-specified data, not missing wires.
- Failure modes in hardware are physical wear and are listed per component; software faults are systematic, so "failure mode" of a function is mostly bad input, dependency failure and state corruption.
- Start-up, shutdown and maintenance are mission phases in hardware; in software they are easy to forget because there is no launch event.
- Parnas's subset idea has no hardware analogue and is the main software-only input: functions can be ordered by a "uses" relation so that useful subsets exist (conditions (a) to (d) in section "Uses relation", VERIFIED). It supports increment selection and an ordering check on function dependencies: a function in the minimal subset must not need a function outside it (INFERRED check).
- Cockburn goal levels exist for interactive software and do not fit internal blocks (INFERRED).
