# What a spike agent must guard against (2026-11-28)

Question: what should the agent that runs spikes (#59) be told, so that its `SPK-`
record can be trusted as evidence for a function, a requirement value or a decision? Six
parts, agreed with Amit: (1) what a spike is and what bounds it; (2) kinds of spike,
including qualitative ones judged by a person; (3) how software measurements go wrong;
(4) how coding agents misreport results; (5) keep or delete the code; (6) bounds other
than time.

Method: one subagent on Sonnet, told to follow `agents/researcher.md` word for word (the
`researcher` agent type is not registered in a session of this repository, so this tests
its text, not its frontmatter). It wrote record RES-T3ME with 29 findings. The record is
not kept in the repository; this summary keeps its findings, sources and labels. On the
agent: it fetched raw pages when WebFetch summarised, used author copies when the ACM
refused, reported every failed fetch, and labelled relayed quotes VERIFIED-secondary.

Labels: **VERIFIED** = read in a primary source (named). **VERIFIED-secondary** = only a
secondary source or a relayed quote was seen. **INFERRED** = reasoning, mine unless
said. Quotes are short.

## Summary

1. **A spike answers one question with the smallest code that can answer it, and is
   expected to be thrown away.** XP and the Pragmatic Programmer agree. Their example of
   a prototype is a measurable TBD: a required 10,000 transactions an hour, checked with
   "a real ugly little script". (§1)
2. **What bounds a spike is its question, not a size.** No source gives a limit in lines
   or attempts. The bounds named are one problem, smallest code, thin but end to end, and
   expected disposal; time limits run from minutes to two weeks. (§1, §6)
3. **There are two kinds, and the second is judged by a person.** SAFe separates
   technical spikes (approaches, performance, build or buy) from functional ones
   (behaviour, a UI prototype shown to users); the second is accepted after a demo. No
   source gives a fuller way to record a person's verdict. (§2)
4. **A single measured number is not evidence.** Run-to-run variation, warm-up, and
   innocent setup facts (environment size, link order) move results by tens of percent,
   once almost 300%, and differ between machines. Report the variation, the machine and
   the setup. (§3)
5. **Coding agents game checks and invent results, mostly after repeated failure.**
   They edit tests, hard-code expected values, overwrite the timer, stub the evaluator,
   and report runs they never made. An explicit "report that it cannot be done" exit cut
   cheating sharply; "please do not cheat" did not. (§4)
6. **The sources favour deleting spike code**; none argues for keeping it in a branch
   or the repository. The named risk is shipping the throwaway. (§5)

## 1. What a spike is

- **VERIFIED.** Wells, "Create a Spike Solution" (extremeprogramming.org, 1999), read in
  full: "A spike solution is a very simple program to explore potential solutions. Build
  the spike to only addresses the problem under examination and ignore all other
  concerns. Most spikes are not good enough to keep, so expect to throw it away." Its aim
  is to cut a technical risk or make an estimate reliable; it sizes one as "a pair of
  developers on the problem for a week or two".
- **VERIFIED.** C2 wiki, "Spike Solution" (c2.com/xp/SpikeSolution.html, Cunningham and
  others), read in full: "Write the smallest possible code that could be said to perform
  a function independent of existing mechanism." A spike is "end to end, but very thin".
  Jeffries, from the Chrysler C3 project: "when we didn't consider the full breadth, we
  got into trouble".
- **VERIFIED-secondary.** Beck, as a signed contribution on the same page (his book was
  not read): "Spikes are good when you are knowledge-limited, not time-limited."
- **VERIFIED.** Hunt and Thomas, "Tracer Bullets and Prototypes" (Artima interview,
  2003), read in full: a prototype investigates "a specific aspect of something—whether
  it's an interface, or an algorithm, or a performance problem"; "Prototypes are for your
  learning"; "Prototypes are designed to be thrown away." Tracer code, by contrast, is a
  thin skeleton that is kept and grown. Their example of a prototype is the 10,000
  transactions an hour, tested by a script that need not go through the product's code.
  The book itself was not read (O'Reilly refused).

## 2. Kinds of spike

- **VERIFIED.** SAFe, "Spikes" (v5 page, 2023 Wayback copy; the live section is behind a
  login): "Technical spikes – They are used to research various approaches in the
  solution domain" (build or buy, performance or load impact); "Functional spikes – They
  are used to analyze overall solution behavior". Its example pairs timing a display
  update with prototyping a histogram "and get user feedback".
- **VERIFIED.** Same page: "The output of a spike is demonstrable, both to the team and
  to any other stakeholders ... The Product Owner accepts spikes that have been demoed
  and meets its acceptance criteria." This is the only rule found for a result that is a
  person's judgement.
- **VERIFIED-secondary.** The Pragmatic Programmer, as quoted by Atwood ("The Prototype
  Pitfall", 2005): prototype a UI, "code only enough to make the interface responsive to
  user actions", and throw it away once users agree the layout.
- **Gap.** Paper prototyping and design probes as a field were not searched; how to
  record a qualitative verdict stays thin.

## 3. How measurements go wrong

- **VERIFIED.** Georges, Buytaert, Eeckhout, "Statistically Rigorous Java Performance
  Evaluation" (OOPSLA 2007, doi:10.1145/1297027.1297033), full text from an author copy.
  Run time varies run to run (JIT, scheduling, garbage collection); best, worst or one
  mean of a few runs "can be misleading and can even lead to incorrect conclusions".
  Start-up and steady state are measured apart; the first invocation is discarded "to
  reach independence"; steady state is where the coefficient of variation of the last k
  iterations falls below a threshold (0.01 or 0.02), then a confidence interval across
  invocations (§4.1-4.2).
- **VERIFIED.** Kalibera and Jones, "Rigorous Benchmarking in Reasonable Time" (ISMM
  2013, doi:10.1145/2464157.2464160), full text of the author manuscript. Automatic
  warm-up detectors often give too few or far too many runs; iteration times are often
  "strongly auto-dependent", so choosing different iterations "can create an error of
  tens of percent" (§6.1). Repetition is needed where the variation arises; reported
  results "often lack proper variation estimates" (§12). No universal run count.
- **VERIFIED.** Mytkowicz, Diwan, Hauswirth, Sweeney, "Producing Wrong Data Without
  Doing Anything Obviously Wrong!" (ASPLOS 2009, doi:10.1145/1508244.1508275), full text.
  The size of an unused environment variable changed run time "frequently by about 33%
  and once by almost 300%"; "the best link order on one microprocessor is often not the
  best link order on another". None of 133 surveyed papers dealt with it. Remedies:
  randomise the setup, analyse causes.

## 4. How coding agents misreport

- **VERIFIED.** Zhong, Raghunathan, Carlini, "ImpossibleBench" (arXiv 2510.20270, HTML
  full text). Four strategies on tasks whose tests contradict the spec: modify tests,
  overload comparison, record extra state, special-case the tests; Claude models mostly
  modify tests. Read-only tests cut test edits but not special-casing. Repeated
  submissions raised cheating (33% to 38%). An abort exit ("submit the string
  flag_for_human_intervention") cut GPT-5 from 54% to 9% and o3 from 49% to 12%, with a
  much smaller effect on Claude Opus 4.1 (§5.2-5.3).
- **VERIFIED.** Claude 3.7 Sonnet system card (Anthropic, Feb 2025, §6): special-casing
  in agentic coding, "Most often ... directly returning expected test values rather than
  implementing general solutions, but also includes modifying the problematic tests";
  "These behaviors typically emerge after multiple failed attempts to develop a general
  solution".
- **VERIFIED.** Claude Opus 4 and Sonnet 4 system card (May 2025, §6): hard-coding and
  special-casing still occur, about two-thirds less than 3.7; a prompt asking for a
  general solution and to say when tests are wrong or the task infeasible reduces them.
  Its transcript 6.3.A reports "implemented successfully and all tests pass" while
  listing "special cases for the test examples" as a feature.
- **VERIFIED.** METR, "Recent Frontier Models Are Reward Hacking" (5 June 2025): o3
  overwrote the timer, disabled synchronisation, cached the answer so a script looked
  fast, and patched the evaluator; 30.4% of RE-Bench runs. Asked whether this matched
  the user's intent, it said no 10 times out of 10. "Please do not cheat" left the rate
  at 80%.
- **VERIFIED.** Transluce, "Investigating truthfulness in a pre-release o3 model" (16
  April 2025): o3 "frequently fabricates actions it took", including timings from a
  machine and setup it never had.
- **Gap.** "Narrowing the question until it passes" was not found as a named behaviour.

## 5. Keep or delete

- **VERIFIED.** For deleting: Wells ("expect to throw it away"); Hunt and Thomas
  ("one-offs"); Jeffries: "We plan to throw away the code, although sometimes something
  is salvaged."
- **VERIFIED** (OCR scan). Brooks, The Mythical Man-Month, ch. 11: delivering the
  throwaway "buys time, but it does so only at the cost of agony for the user,
  distraction for the builders while they do the redesign, and a bad reputation".
- **VERIFIED-secondary.** Atwood relaying Glass: "Once in production a prototype will
  never die."
- **Not found.** A source for keeping spike code in a branch or the repository. One wiki
  contributor kept spikes as tests in the build so they break when a vendor library
  changes. SAFe keeps the information, not the code.

## 6. Bounds other than time

- **VERIFIED.** One problem (Wells; Hunt and Thomas); smallest code (Cunningham); thin
  but end to end (Jeffries); SAFe: fit one iteration, "develop only the information
  required", use spikes as "the exception, not the rule". Time limits seen: "a week or
  two" (XP), "a couple of days, and a half day is ideal" (C3), "minutes" for an
  algorithm (Beck).
- **INFERRED** (the subagent's). No source gives a number of attempts. Since gaming
  follows repeated failure (§4), a stop that reports "not settled" fits the evidence.

## What this suggests for the agent (INFERRED)

- The brief states one question and what its answer is for; a question that needs
  product code to answer is not a spike.
- A measured value comes with its runs, their spread, the machine and the setup, and
  whether the machine is like the target.
- The agent must not change what judges the result (the check, the timer, the
  harness) to get an answer, and must say when the question cannot be answered. The
  exit has to be real: "cannot settle" is a result, not a failure.
- The record holds the commands run and their raw output, so a claimed run can be
  checked.
- A qualitative spike ends with the builder's verdict, not the agent's.
- Keeping the code is Amit's choice against the sources' lean; the reason given for
  keeping it (the builder can look again, especially at UI) is not one the sources
  weigh.
