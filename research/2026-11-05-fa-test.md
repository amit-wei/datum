# Functional-analysis test: does the step beat no skills at all? (2026-11-05)

The test and its raw results are in `experiments/2026-11-05-fa-test/` (behaviours,
prompts, pass criteria and the decision rule in `queries.md`; runs in `results/`).
VERIFIED means seen in these runs; INFERRED means our reading of them.

**Question** (#6, #23): does the functional-analysis step, with its techniques, beat no
skills at all on the same fixtures? And does `losses-and-hazards` keep a child part to
the hazards it introduces?

**Method:** 14 behaviours on 6 fixture projects (a fictional climbing log), one turn per
query. Datum ran with the plugin and a CLAUDE.md line; the baseline ran the same fixture
with neither. A Sonnet judge compared each run with an Outcome written before the run,
on substance only, so the baseline was not failed for lacking datum's formats. Split:
8 train, 6 validation. Haiku pilots on train, then Sonnet on all 14, then three reruns of
the behaviours the test had got wrong. 76 recorded runs, about $10.80, against a budget of
$3–5.

**Limits:**
- Most behaviours had one run per variant: a direction, not a measurement.
- Validation and rerun verdicts were read by hand, from each run's final message. On the
  train set only B8 and B14 were; the others rest on the judge and its stated reason.
- The baseline read fixtures already written in datum's structure, which helps it. A
  builder starting without datum has no such model. INFERRED.
- B2 and B11 were rerun after being seen, so those reruns are evidence, not a held-out
  check. Fixtures D1–D3 changed between runs.
- The rig refused compound shell commands, so no run could run the validator itself. The
  rig's own check after each datum run found no errors. VERIFIED.
- Only functional analysis was tested. Nothing here shows what happens downstream.

## Decision

- **Keep the step and its techniques:** they clear the bar of beating a no-skill baseline.
- **Datum's value at this step is process discipline, not sharper analysis.** It stops
  the agent acting early or overbuilding, and it keeps the work moving. INFERRED. The
  working theory: discipline here narrows synthesis and targets building. Untested.
- **Grilling is forced only when a part has no elicitation record,** at every part.
  `steps.yaml` closes only with the step, so without this the agent grills a part again
  (all six datum runs on the first rerun, none after the change). VERIFIED.
- **The same state by another cause is not a new hazard.** If no parent requirement covers
  that cause, it goes up as an issue.
- **#23 closed by decision,** though the rule set before the test was not
  met (B11r 1/3). What remains is wider than #23: forced techniques do not always load
  (#25).

## Lessons for writing datum's skills

1. **A technique works only if it loads, and "forced" does not make it load.** Two of six
   runs skipped `losses-and-hazards` although the step forces it, when the functions
   already existed. VERIFIED. Open in #25.
2. **"Forced once" needs a condition the agent can check on disk.** "Once" means nothing to
   a new session. Name the file that shows it happened. VERIFIED.
3. **A technique's rule must settle the near case.** "New only if no parent requirement
   answers it" and "causes come later" disagreed on a wrong load estimate until a rule
   decided it. With the rule, one run used its exact words. VERIFIED.
4. **The agent takes the first open obligation it finds.** Datum stopped at missing
   functions before it reached hazards, which is right, and raised them unprompted.
   Order in the end condition matters less than what is still open. INFERRED.
5. **A bare question can bypass datum.** "How fast does the suggestion need to be?" entered
   no skill on Sonnet or Haiku, despite the CLAUDE.md line; Sonnet did not read the repo.
   VERIFIED. Open in #25.
6. **On an empty repository nothing points at datum.** Haiku wrote a codebase; Sonnet
   loaded datum. Same gap as packaging-test lesson 2. VERIFIED.
7. **Stating what a function must not contain works.** On Haiku, datum wrote four functions from
   four scenarios with no mechanism or number. The "look for what is missing" list in
   `writing-functions` still contradicts its "Needed" rule, but it did not cause
   overbuilding here. VERIFIED, one run.

## Lessons for testing a step

8. **Walk each fixture through the step's end condition before any run.** A fixture with
   gaps of its own hides the behaviour under test: D2 and D3 lacked two functions, and
   the agent rightly raised those first. VERIFIED.
9. **A one-turn test stops at the first thing the agent must ask,** so a fixture must be
   clean up to the behaviour, or the behaviour is never reached. Forced grilling made one
   version of B11 pass with nothing tested. VERIFIED.
10. **Do not name the behaviour in the prompt.** "Could anything hurt someone?" made the
    technique look unnecessary; "carry on" showed the difference. VERIFIED.
11. **Do not write a prompt that orders the failure.** An explicit "work around it" from
    the builder makes the pass ambiguous; let the agent find the problem. INFERRED.
12. **Give the rig what the skills need.** Refused shell commands stopped ID-making and the
    stale check, and looked like a skill failure in B2. Check refusals in a pilot.
    VERIFIED.
13. **Read the runs.** The Sonnet judge gave at least four wrong verdicts among those read,
    in both directions, and rated near-identical content differently. Its verdict alone
    would have flattered datum on B11 and B14. VERIFIED.
14. **A pass needs the mechanism as well as the verdict.** A datum run passed B8 in the
    pilot with nothing loaded, so the pass was not datum's. Report whether datum loaded
    beside every verdict. VERIFIED.
15. **Compare behaviour by behaviour; quote no percentage.** With six validation behaviours,
    4 of 5 passing would allow a true rate of 28% to 99% (exact 95% interval). The split
    guards against tuning to the test; it estimates nothing. The usual 80/20 and 70/30 are
    rules of thumb, and we kept the 60/40 of the packaging test. INFERRED.
16. **Same prompt, two fixtures tests discrimination,** but only if the fixtures truly
    differ. D2 was meant to bring no hazard, and every run found real ones. VERIFIED.
17. **Set the rerun limit before starting.** Three reruns doubled the budget. Each found
    something real, but most were faults lesson 8 would have caught for free. INFERRED.
