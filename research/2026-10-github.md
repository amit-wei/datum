## What an agent can drive

- **gh CLI:** issues, PRs, projects, and `gh api`.
- **GitHub MCP server** (V, https://github.com/github/github-mcp-server):
  - Default toolsets: context, repos, issues, pull_requests, users. Others are opt-in.
  - Tools: sub-issue tools, `projects_*`, Actions runs, jobs, artifacts and logs, and
    `assign_copilot_to_issue`.
- **Rate limits** (V):
  - 5,000 requests/hour per user token.
  - `GITHUB_TOKEN` in Actions: 1,000/hour.
  - Secondary limits of about 80 content creations a minute and 500 an hour, so bulk
    issue creation needs batching.
- **claude-code-action** (V):
  - Triggers: `@claude` in issues and PRs, issue assignment, or an explicit prompt.
  - Auth: API key, Bedrock, Vertex or Foundry. Whether subscription auth works is
    unverified.

## Evidence and its retention

- **Rulesets and branch protection** (V/INF): Free accounts get them on public repos
  only; private repos need Pro. Verified on this public Free repo: `gh api
  repos/amit-wei/datum/rulesets` returns 200 (`[]`), and `.../branches/main/protection`
  returns 404 "Branch not protected", not a plan-upgrade 403. The docs page
  (githubs-plans) lists protected branches under Pro for private repos; the private-repo
  half is INF, and rulesets are not named there.
- **Check runs** (V):
  - Creating one needs a GitHub App. A workflow job is already a check run.
  - Limits: 50 annotations per request; 10 warnings and 10 errors per Actions step.
- **Job summaries:** 1 MiB per step (V). Readable, but not queryable later.
- **Retention** (V): **90 days by default** for artifacts, logs, checks, runs and
  statuses. Since 2026-10-01 that also covers checks, runs and commit statuses. **CI is
  not durable evidence.**
- **Attestations** (V): signed provenance for a commit SHA. Custom predicates could carry
  test evidence (INF). Probably overkill for a solo builder.

**Most robust evidence storage, ranked** (INF):

1. A compact evidence record committed to the repo: proof ID, tested SHA, result, run
   URL, timestamp, log digest.
2. Full reports as release assets for each version.
3. Checks and job summaries as the live view only.
4. Optional attestation for tamper evidence.

## Releases and milestones

Milestones work on this repo (V: `gh api repos/amit-wei/datum/milestones`). The releases
endpoint answers 200 with none yet (V); creating one is unproven (INF). The mapping
below is a design proposal (INF).

- Milestone = increment.
- Release = the immutable close of an increment: a tag, generated notes, evidence
  assets.
- Conventional commits with `gh release create --generate-notes` give a changelog.

## Sync patterns

- The common pattern is **one-way: files first, then issues generated from them** with
  IDs in the issue body. Example: the community Spec Kit `taskstoissues` skills (V by
  search).

**Files vs issues for decisions and open questions:**

| | Files | Issues |
|---|---|---|
| Offline access, agent access, grep | strong | needs the API |
| CI validation, supersession links | strong | weak |
| Pinned to a version | per commit | editable |
| Portable off GitHub | yes | no |
| Inbox, discussion, notifications, capture from a phone | weak | strong |

## The agent's recommended split

- **Repo files: the authoritative record.**
  - The model: functions, requirements, parts, interfaces, risks.
  - Decisions (with `supersedes`) and open questions, with status.
  - Proof definitions, an evidence index, and `CHANGELOG.md`.
- **GitHub: intake and work, not authoritative.**
  - Issue forms with `type:*` labels for intake.
  - Triage closes an issue with a link to the file ID it became.
  - A milestone per increment. Task issues are generated from the files, carry requirement
    and proof IDs, and are ordered with sub-issues and blocked-by.
  - A PR template lists the IDs touched.
  - CI runs the proofs. A bot commit writes the evidence index. A release attaches the
    reports.

**Sync rules:**

1. Files own IDs. Issues reference them and never hold the only copy.
2. Flow is intake → file.
3. Task issues are generated from the files.
4. The validator checks the links and checks that evidence is fresh for HEAD. Evidence
   goes stale when files within a proof's scope change.
5. Losing GitHub loses only intake and discussion.
